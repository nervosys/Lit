# NIST SP 800-171r3 — Control Mapping for Self-Hosted Lit

**Target:** NIST SP 800-171 Revision 3 (May 2024)
**Applies to:** Lit 1.6.0+ run as a self-hosted server via `lit server serve`
**Status of this document:** engineering mapping, not an assessment

---

## 1. Read this first

**Lit is not "800-171 compliant," and no software is.** SP 800-171 applies to an
*organization's system* that processes, stores, or transmits Controlled
Unclassified Information. Compliance is a property of that system — its people,
its network, its physical facility, its policies — and is asserted by the
organization, assessed against NIST SP 800-171A, and scored under DFARS
252.204-7012 / 7019 / 7020 where a contract requires it.

What this document does is narrower and more useful: for each requirement, it
states **what Lit does, what Lit gives you a knob for, and what Lit leaves
entirely to you**. That is the input an SSP author needs. Anything here that
reads like a compliance claim is a defect in this document; please report it.

Two further cautions, stated up front because they are the ones most likely to
cost you in an assessment:

1. **Lit's TLS is not FIPS-validated.** See §5.1. If your system must
   demonstrate FIPS-validated cryptography protecting CUI in transit, you must
   terminate TLS in a validated module in front of Lit. Lit will happily serve
   `https://` either way, and the difference is invisible from outside.
2. **The requirement text in this document is a paraphrase.** Requirement
   identifiers and titles are given so you can find them, but assess against the
   published SP 800-171r3 and SP 800-171A, not against this table. Where the
   paraphrase and the standard disagree, the standard wins.

### Status vocabulary

| Status | Meaning |
| --- | --- |
| **Implemented** | Lit provides the mechanism and it is on by default. |
| **Configurable** | Lit provides the mechanism; it is off, or weak, until you configure it. |
| **Partial** | Lit provides part of what the requirement asks for. The remainder is yours. |
| **Customer** | Lit provides nothing. The requirement is satisfied outside Lit. |
| **N/A** | The requirement has no meaning for a headless service. Stated, not claimed. |

## 2. What changed to make self-hosting viable

Before this work, `lit serve` was a development convenience: bound to
`127.0.0.1`, plaintext HTTP, one shared bearer token, and no audit output. A
shared token cannot identify *who* acted, which means no audit record it
produced could satisfy `03.03.02` — and audit is the control family every
investigation depends on.

`lit server serve` is a separate command with different defaults:

| Capability | `lit serve` (dev) | `lit server serve` (hosted) |
| --- | --- | --- |
| Bind address | `127.0.0.1` only | Configurable, TLS required off-loopback |
| Transport | HTTP | HTTPS, or HTTP on loopback |
| Authentication | Optional shared token | Named accounts, PBKDF2-HMAC-SHA512 |
| Authorization | None | Four roles, decided in one place |
| Sessions | None | Idle + absolute timeout, revocable |
| Lockout | None | Windowed, configurable |
| Banner | None | Operator-supplied, served pre-auth |
| Audit | None | Every decision, HMAC-chained |

They are separate commands rather than flags because conflating them is exactly
how a development server ends up on a routable address.

## 3. Family-by-family mapping

### 03.01 — Access Control

| ID | Requirement | Status | How |
| --- | --- | --- | --- |
| 03.01.01 | Account management | **Implemented** | `lit server user add/list/role/disable/enable/remove/unlock`; store at `~/.lit/server/users.json`, owner-only. The last enabled admin cannot be removed, demoted, or disabled. |
| 03.01.02 | Access enforcement | **Implemented** | `server::required_role` is the single authorization decision point. Unlisted routes fail closed to `Admin`. |
| 03.01.03 | Information flow enforcement | **Partial** | `network::validator` enforces an allow-list of networks and hosts for outbound transport; airgap mode (`network::airgap`) blocks network egress entirely. Flow control *between* CUI and non-CUI repositories is yours. |
| 03.01.04 | Separation of duties | **Customer** | Lit's roles let you express a separation; deciding what that separation is, is organizational. |
| 03.01.05 | Least privilege | **Implemented** | Four ordered roles. New accounts default to `reader`. Read routes need `reader`, commits need `contributor`, history-altering operations need `maintainer`, account administration needs `admin`. |
| 03.01.06 | Least privilege — privileged accounts | **Configurable** | Give administrators a separate `admin` account from their day-to-day `contributor` account. Lit does not enforce this. |
| 03.01.07 | Privileged functions | **Implemented** | Administrative routes live under `/api/v1/admin/`, require `admin`, and every invocation emits an `ACCOUNT_CHANGE` audit record. |
| 03.01.08 | Unsuccessful logon attempts | **Implemented** | Windowed lockout, default 5 failures in 15 minutes → 15-minute lock. `--max-attempts`, `--lockout-secs`; `0` locks until an administrator clears it. |
| 03.01.09 | System use notification | **Configurable** | Served at `GET /api/v1/banner` before authentication. Lit ships a placeholder that **says it is a placeholder**; set `--banner` to your approved wording. The server warns at startup while the placeholder is in use, and records it in the audit log. |
| 03.01.10 | Device lock | **N/A** | No interactive session on a device. The analogous protection is session inactivity termination — see 03.01.11. |
| 03.01.11 | Session termination | **Implemented** | Idle timeout (default 15 min) and absolute lifetime (default 8 h), enforced on use, not merely on a sweep. `POST /api/v1/auth/logout` terminates explicitly. Removing an account terminates its live sessions. |
| 03.01.12 | Remote access | **Partial** | Remote access is authenticated, authorized, TLS-protected, and logged. Routing it through a managed access control point is yours. |
| 03.01.16–03.01.18 | Wireless access | **Customer** | Outside Lit. |
| 03.01.20 | External systems | **Partial** | Federation peers and remotes are restricted by `network::validator`'s allow-list. Which externals are authorized is yours. |
| 03.01.22 | Publicly accessible content | **Customer** | Lit does not distinguish public from CUI repositories. Do not host both from one server. |

**Known gap:** a role change does not retroactively downgrade a live session;
it takes effect when that session expires. `lit server user remove` *does*
terminate sessions immediately. If you need an immediate downgrade, disable the
account (which terminates nothing today) and restart the server — or remove and
recreate. This is the sharpest edge in the current implementation.

### 03.03 — Audit and Accountability

| ID | Requirement | Status | How |
| --- | --- | --- | --- |
| 03.03.01 | Event logging | **Implemented** | The logged event set is the `ServerEvent` enum: `SERVER_START/STOP`, `AUTH_SUCCESS/FAILURE/LOCKOUT`, `SESSION_INVALID/END`, `ACCESS_DENIED`, `API_REQUEST`, `ACCOUNT_CHANGE`, `RATE_LIMITED`, `REQUEST_REJECTED`. |
| 03.03.02 | Audit record content | **Implemented** | Every record carries timestamp, event type, subject (username), source address, object (route or account), outcome, and reason on failure. |
| 03.03.03 | Audit record review | **Customer** | Lit writes; it does not review. Ship the log to your SIEM. |
| 03.03.04 | Response to audit logging failures | **Partial** | A failed write is reported on stderr with the event that was lost. Lit does **not** stop serving when the audit log is unwritable. If your policy requires it to, run it under a supervisor that watches stderr for `AUDIT FAILURE`. |
| 03.03.05 | Audit correlation | **Customer** | Correlate in your SIEM. Records are single-line and machine-parseable to make this cheap. |
| 03.03.06 | Audit reduction and reporting | **Partial** | Records are `timestamp \| event \| json \| hmac`. No query tooling ships with Lit. |
| 03.03.07 | Time stamps | **Implemented** | RFC 3339, UTC. Host clock synchronization is yours. |
| 03.03.08 | Protection of audit information | **Implemented** | Each record is HMAC-SHA256 signed under a key stored owner-only; `lit verify` checks the chain. The log file itself is owner-only on both Windows and Unix. |

**Known gap:** the audit log is append-only *by convention*, not by enforcement.
A local administrator can truncate it; the HMAC makes tampering with existing
records detectable, but does not make deletion detectable. Forward records off
the host promptly if that matters.

### 03.05 — Identification and Authentication

| ID | Requirement | Status | How |
| --- | --- | --- | --- |
| 03.05.01 | User identification and authentication | **Implemented** | Unique named accounts; every request resolves to one. |
| 03.05.02 | Device identification | **Customer** | Use mutual TLS at your proxy if you need it; Lit does not authenticate devices. |
| 03.05.03 | Multi-factor authentication | **Customer — GAP** | **Lit does not implement MFA.** For a system requiring MFA for privileged and network access, put an authenticating reverse proxy (SSO/OIDC with MFA) in front of Lit and bind Lit to loopback. See `docs/SELF_HOSTING.md` §4. |
| 03.05.04 | Replay-resistant authentication | **Partial** | Session tokens are 256-bit random, transported under TLS, and expire. This is not a replay-resistant mechanism in the sense the control means; TLS provides the replay resistance. |
| 03.05.05 | Identifier management | **Implemented** | Usernames are unique and are not reused while the account exists. Lit does **not** prevent reuse after deletion; if your policy forbids it, enforce it in your provisioning process. |
| 03.05.07 | Password management | **Partial** | Minimum 15 characters, maximum 256, may not contain the username, may not be a short repeated sequence. Stored as PBKDF2-HMAC-SHA512, 600,000 iterations, 128-bit random salt, constant-time comparison. **No breached-password check and no reuse history** — both need data Lit does not ship. |
| 03.05.11 | Authentication feedback | **Implemented** | Passwords are never echoed; there is no `--password` flag precisely because arguments are visible in the process table. Passwords come from `--password-file`, `--password-stdin`, or `LIT_SERVER_PASSWORD`. |
| 03.05.12 | Authenticator management | **Partial** | `lit server user password` rotates; rotation *policy* is yours. |

## 4. Customer responsibility summary

The requirements Lit contributes **nothing** to, which you must satisfy entirely
outside it: all of 03.02 (training), 03.06 (incident response), 03.07
(maintenance), 03.09 (personnel), 03.10 (physical), 03.15 (planning), 03.16
(acquisition), plus 03.05.03 (MFA) and 03.08.04 (CUI marking).

The requirements where Lit gives you a mechanism that is **off or weak by
default**, and which will be findings if you deploy without configuring them:

1. `03.01.09` — the system use notification is a placeholder until you set `--banner`.
2. `03.13.08` / `03.13.11` — TLS is off unless you pass `--tls-cert` / `--tls-key`, and is not FIPS-validated even then.
3. `03.03.01` — auditing is on by default but writes to `~/.lit/audit.log`; forward it off-host.
4. `03.01.06` — separate privileged accounts from day-to-day accounts yourself.
5. `03.05.03` — MFA requires a proxy.

## 5. The honest gap list

### 5.0 Revoking an account does not end the sessions it already holds

**This was worse.** `lit server serve` used to load the account store once at
startup and write its in-memory copy back on every successful login, so a
`lit server user …` command run against a running server was invisible to it
*and* was then erased — `disable bob` reported success while Bob kept logging
in. `UserStore` now re-reads the file whenever its modification time or length
has changed, before authenticating, before listing, and before every mutation.
CLI administration of a running server works.

Sessions no longer outlive the authority they were issued under, either. Every
request re-checks the account behind its session against the (refreshed) store,
and a session whose account has been removed or disabled is terminated on the
spot; a demoted account's session drops to its current role rather than the one
it was minted with. So a CLI `disable`, `role`, or `remove` bites on the
revoked user's very next request, not whenever their session happened to expire.

This is the behaviour `03.09.02` (personnel termination) is tested by, so it is
worth verifying yourself rather than taking on trust — `docs/SELF_HOSTING.md`
§6 step 11 does exactly that.

Two things remain:

1. **A residual lost-update race.** Two processes that both write between one
   another's refresh and save can still lose an update. The window is small and
   needs simultaneous administration from two places; closing it properly needs
   file locking, which is not implemented.

2. **`disable`, `enable`, `role`, `password`, and `unlock` have no API
   equivalent.** Only create, list, and delete are exposed. Use the CLI for the
   others — which now works against a running server.

### 5.0b Behind a proxy, configure `--trusted-proxy` or the audit source is wrong

Lit identifies a client by the TCP peer address. Behind the **recommended** FIPS
deployment in §5.1 — TLS terminated in a validated proxy, Lit on loopback — that
is always `127.0.0.1`, so without further configuration every audit record names
the proxy rather than the client, and the per-address rate limiter becomes one
shared bucket.

`--trusted-proxy <IP>` fixes both: `X-Forwarded-For` is believed on connections
from the addresses you name, and the client address it reports is what the rate
limiter buckets on and what the audit log records. The header is **ignored**
otherwise, which is the safe default — it is caller-supplied, and believing it
from anyone would let every client choose its own `03.03.02` source address.

This is configuration, not a property you get for free, and it is easy to miss
because nothing looks broken without it. Two checks worth making before an
assessment:

- `--trusted-proxy` names every proxy address, and your proxy sets
  `X-Forwarded-For` with something equivalent to nginx's
  `$proxy_add_x_forwarded_for` — appending what it actually received from, not
  passing through whatever the client sent.
- A failed login from a real client shows **that client's** address in
  `~/.lit/audit.log`, not the proxy's. This is a one-minute check and it is the
  evidence `03.03.02` rests on.

### 5.1 TLS is not FIPS-validated

Lit terminates TLS with `rustls`, whose default cryptographic provider is not a
FIPS 140-3 validated module. Lit's *at-rest* cryptography does go through the
FIPS module in `crypto::fips`, with power-on self-tests. Its TLS does not.

`03.13.11` requires FIPS-validated cryptography to protect CUI. If that applies
to your system, the supported arrangement is:

```
client ──TLS(FIPS-validated terminator)──> nginx/HAProxy/stunnel ──loopback──> lit server serve
```

Bind Lit to `127.0.0.1`, let the validated module do the TLS. This is documented
in the source as well as here, because both arrangements serve `https://` and
the difference is not observable from outside.

### 5.2 No multi-factor authentication

Stated at 03.05.03. Solved with the same proxy.

### 5.3 A role change does not downgrade a live session

Stated under 03.01. `remove` terminates sessions; `disable` and `role` do not.

### 5.4 `.lit/HEAD` is written in the clear

Carried over from `docs/HANDOFF.md` §3. Branch names are disclosed even when
repository encryption is configured.

### 5.5 No CUI marking

Stated at 03.08.04.

### 5.6 The audit log can be truncated by a local administrator

Stated under 03.03. Tampering is detectable; deletion is not.

### 5.7 Single-threaded request handling

`lit server serve` handles one request at a time. This is an availability
characteristic, not a confidentiality one, and 800-171r3 does not address
availability — but a slow request is a denial of service against your users, so
size the deployment accordingly and put a proxy in front.

## 6. Verifying the claims

Every "Implemented" above is backed by a test. To check them yourself:

```bash
# The access control, session, lockout, banner, and TLS mechanisms
cargo test --lib server::

# The audit chain, including tamper detection
cargo test --lib audit

# FIPS power-on self-tests
cargo test --lib fips
```

To see the controls working end to end, `docs/SELF_HOSTING.md` §6 walks through
starting a server, being refused, authenticating, being denied for privilege,
and reading the resulting audit records.
