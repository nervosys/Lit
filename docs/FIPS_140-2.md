## Overview

Lit implements **FIPS 140-2** (Federal Information Processing Standards Publication 140-2) security requirements for cryptographic modules. This ensures compliance with U.S. government standards for protecting sensitive information.

## FIPS 140-2 Standard

**FIPS 140-2** specifies security requirements for cryptographic modules used within security systems protecting sensitive information. Published by NIST in 2001, it defines four security levels (1-4) with increasing security requirements.

### Lit's Security Level

**Target: FIPS 140-2 Level 1**
- Software-based cryptographic module
- Approved cryptographic algorithms
- Self-tests (power-on and conditional)
- Role-based authentication
- Secure key management with zeroization

## FIPS 140-2 Requirements Implementation

### 1. Cryptographic Module Specification (Section 4.1)

#### Module Definition
- **Name**: Lit Cryptographic Module
- **Type**: Software cryptographic module
- **Version**: 0.1.0
- **Description**: Quantum-resistant version control system with FIPS-approved cryptography
- **Boundary**: Software module within Lit binary
- **Platform**: Cross-platform (Windows, Linux, macOS)

#### Approved Algorithms
Lit uses only FIPS-approved cryptographic algorithms:

| Algorithm    | FIPS Standard | Use in Lit                               |
| ------------ | ------------- | ---------------------------------------- |
| SHA-256      | FIPS 180-4    | Content hashing (backward compatibility) |
| SHA-512      | FIPS 180-4    | Primary content hashing (FIPS mode)      |
| SHA3-512     | FIPS 202      | Quantum-resistant hashing                |
| HMAC-SHA-256 | FIPS 198-1    | Message authentication                   |
| HMAC-SHA-512 | FIPS 198-1    | Message authentication                   |
| AES-256      | FIPS 197      | Future encryption support                |

### 2. Cryptographic Module Ports and Interfaces (Section 4.2)

#### Interfaces
- **Data Input**: File system operations, network (intranet only)
- **Data Output**: File system operations, network (intranet only)
- **Control Input**: CLI commands, configuration files
- **Status Output**: Logs, audit trails, FIPS status indicators

#### Physical Ports
- Software module, no physical ports

### 3. Roles, Services, and Authentication (Section 4.3)

#### Roles
1. **User**: Standard repository operations
   - Read/write repository data
   - Commit, branch, merge operations
   - View cryptographic status

2. **Crypto Officer**: Manage cryptographic functions
   - Configure FIPS mode
   - Run self-tests
   - Manage key material
   - View security parameters

#### Services
| Service          | Role           | Approved Algorithm |
| ---------------- | -------------- | ------------------ |
| Hash Object      | User           | SHA-512, SHA3-512  |
| Sign Commit      | User           | ML-DSA (future)    |
| Verify Signature | User           | ML-DSA (future)    |
| Generate HMAC    | User           | HMAC-SHA-512       |
| Self-Test        | Crypto Officer | All                |
| Status Query     | Both           | N/A                |

#### Authentication
- Operating system authentication (file permissions)
- Role separation through configuration access

### 4. Finite State Model (Section 4.4)

#### States
1. **Power-On**: Initial state, self-tests not performed
2. **Approved Mode**: Self-tests passed, cryptographic operations allowed
3. **Error State**: Self-test failure, cryptographic operations disabled

#### State Transitions
```
Power-On → [Self-Tests Pass] → Approved Mode
Power-On → [Self-Tests Fail] → Error State
Approved Mode → [Error Detected] → Error State
Error State → [Reset] → Power-On
```

- Tamper-evident packaging (digital signatures on releases)

### 6. Operational Environment (Section 4.6)

#### Requirements
- **Operating Systems**: Windows, Linux, macOS
- **Dependencies**: Rust standard library, FIPS-approved crypto libraries
- **Deployment**: Single-user workstations, secure servers

#### Security
- Operating system access controls
- File system permissions
- Process isolation

### 7. Cryptographic Key Management (Section 4.7)

#### Key Types
| Key Type           | Algorithm    | Purpose              | Zeroization |
| ------------------ | ------------ | -------------------- | ----------- |
| Commit Signing Key | ML-DSA       | Sign commits         | Yes         |
| HMAC Key           | HMAC-SHA-512 | Message auth         | Yes         |
| Ephemeral Keys     | Various      | Temporary operations | Yes         |

#### Key Lifecycle
1. **Generation**: Using approved RNG or derived from secure input
2. **Storage**: Encrypted at rest (operating system keychain)
3. **Use**: In-memory only during operations
4. **Destruction**: Secure zeroization using `zeroize` crate

#### Key Zeroization
```rust
use zeroize::Zeroize;

#[derive(Zeroize)]
#[zeroize(drop)]
pub struct SecureKey {
    key_material: Vec<u8>,
}
```
- Automatic zeroization on drop
- Overwrites memory with zeros
- Prevents key material leakage

- No additional requirements

### 9. Self-Tests (Section 4.9)

#### Power-On Self-Tests (POST)
Executed at module initialization:

1. **SHA-256 Known Answer Test (KAT)**
   - Input: `"abc"`
   - Expected: `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`

2. **SHA-512 Known Answer Test**
   - Input: `"abc"`
   - Expected: `ddaf35a193617abacc417349ae20413112e6fa4e89a97ea20a9eeee64b55d39a...`

3. **SHA3-512 Known Answer Test**
   - Input: `"abc"`
   - Expected: `b751850b1a57168a5693cd924b6b096e08f621827444f70d884f5d0240d2712e...`

4. **HMAC-SHA-256 Known Answer Test**
   - Key: `"key"`
   - Message: `"The quick brown fox jumps over the lazy dog"`
   - Expected: `f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8`

5. **RNG Continuous Test**
   - Verifies entropy source
   - Detects RNG failures

#### Conditional Self-Tests
Performed before critical operations:
- Algorithm-specific KATs before first use
- Periodic integrity checks
- Key generation tests

#### Self-Test Failure Handling
```
if self_test_failed {
    log_error("FIPS 140-2 self-test failed");
    enter_error_state();
    disable_crypto_operations();
    notify_administrator();
}
```

## FIPS Mode Operation

### Enabling FIPS Mode

```bash
# Set FIPS mode in configuration
lit config --fips-mode enable

# Verify FIPS mode
lit config --show-fips-status
```

### FIPS Mode Configuration

```toml
# .lit/crypto_config
[fips]
enabled = true
self_tests = true
approved_algorithms_only = true

[algorithms]
hash = "sha512"  # FIPS 180-4
hmac = "hmac-sha512"  # FIPS 198-1
```

### FIPS Mode Behavior

When FIPS mode is enabled:
- ✅ Only FIPS-approved algorithms are used
- ✅ Power-on self-tests run at startup
- ✅ Conditional self-tests before operations
- ✅ Non-approved algorithms disabled (BLAKE3, ML-DSA)
- ✅ Enhanced audit logging
- ✅ Secure key zeroization enforced

## Algorithm Usage

### FIPS-Approved Hash (SHA-512)

```rust
use crate::crypto::fips::FipsHash;

// Hash data using FIPS-approved SHA-512
let data = b"repository content";
let hash = FipsHash::sha512(data);
```

### FIPS-Approved HMAC

```rust
use crate::crypto::fips::FipsHmac;

// Generate HMAC using FIPS-approved HMAC-SHA-512
let key = b"secret key";
let message = b"commit data";
let tag = FipsHmac::hmac_sha512(key, message)?;

// Verify HMAC
FipsHmac::verify_hmac_sha512(key, message, &tag)?;
```

### Self-Tests

```rust
use crate::crypto::fips::FipsModule;

// Initialize FIPS module
let mut fips_module = FipsModule::new();

// Run power-on self-tests
fips_module.power_on_self_test()?;

// Check status
assert!(fips_module.self_test_status());
```
